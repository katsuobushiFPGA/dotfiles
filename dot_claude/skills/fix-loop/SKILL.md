name: fix-loop
description: "チェック系スキル（self-review / check-tests / code-review など）を『実行 → 設計判断が不要な指摘だけ修正 → 再実行』で収束するまで回し、設計判断が必要な指摘は直さずに最後に選択肢付きレポートで問う汎用ループ。`/fix-loop <target-skill> [args] [PR#N] [--max N] [--commit] [--push]` で起動。「self-review を回して直せるものは直して」「PR の指摘を収束するまでループして」と頼まれたときに使う。"
argument-hint: "<target-skill> [args...] [PR#N|<pr-url>] [--max N] [--commit] [--push] [--dry-run] [--worktree <path>] [-- <passthrough>]"
---

あなたはチェック系スキルを収束まで回すオーケストレータです。判断の主役はユーザーで、あなたが勝手に決めてよいのは「設計判断が不要な修正」だけです。

**3 つの約束**:
1. 対象スキルは毎ラウンド `Skill` ツールで丸ごと実行する。手順の省略・部分実行・手動代替をしない（2 回目以降を「前回と同じ」で済ませない）
2. 挙動が変わる修正は自動でしない
3. 迷ったら直さず B（設計判断）に回す

中間出力は各ラウンド末尾の 1 行サマリだけにし、成果は最終レポート 1 本にまとめる。

## 1. 引数の解釈

`$ARGUMENTS` を左から順に解釈する。未知のトークンはすべて対象スキルへ順序を保って渡す。

| 引数 | 意味 | 既定 |
|---|---|---|
| `<target-skill>`（先頭・必須） | `Skill` ツールで呼ぶスキル名。利用可能な一覧に無ければ使い方を出して終了 | — |
| `PR#N` / `#N` / PR URL | PR モード。head ブランチのローカル checkout（worktree）で回す | なし（現在の checkout） |
| `--max N` | 対象スキルの最大実行回数（上限 10） | 5 |
| `--commit` | ラウンド（修正種別）ごとに A 修正をコミットする | しない |
| `--push` | 収束後に head へ push し CI 結果を待つ（`--commit` を含意） | しない |
| `--dry-run` | 1 ラウンドだけ実行し、分類とレポートのみ（修正しない） | off |
| `--worktree <path>` | 対象解決を省略して指定 worktree を使う | 自動解決 |
| `-- ...` | 以降を対象スキルへそのまま渡す（`--max` 等と衝突するときの逃げ道） | — |

- 対象スキルが自前の自動修正オプション（`--fix` 等）を持っていても**渡さない**（渡されたら外して報告）。修正は必ずこのループの分類を通す。

## 2. 対象の解決

### 2-1. PR モード

1. `gh pr view <N> --json number,url,title,headRefName,headRefOid,baseRefName,body,isCrossRepository`。fork（cross-repo）PR は対象外として終了。
2. `git fetch origin <headRefName>`。
3. ローカル checkout を探す（優先順）: `--worktree` 指定 → cwd の現在ブランチが head → `git worktree list --porcelain` で `branch refs/heads/<head>` に一致する worktree → `HEAD <headRefOid>` の detached worktree。
4. 見つからなければ AskUserQuestion で 1 回だけ確認する: (a) `git worktree add --detach <repo>/.worktrees/pr<N> <headRefOid>` で作る (b) 中止。作った場合、依存物・環境（vendor / .env / DB 等）の整え方は**プロジェクトの CLAUDE.md・rules・memory に従う**（このスキルはやり方を知らない）。整わなければ該当 Step が「未実施」になる旨を予告する。
5. checkout の HEAD と `headRefOid` を比べる。後ろ（ancestor）でクリーンなら `git merge --ff-only origin/<head>`、diverged / dirty はレポートに書いて確認する。**未 push のコミット・未コミット差分を絶対に破棄しない。**
6. cwd と違う場所なら `EnterWorktree(path: <path>)` でセッションを切り替える（`context: fork` で動く対象スキルの cwd も追従する）。使えなければ全 Bash を `cd <path> && ...` で始め、Read/Edit は絶対パスにする。終了後は `ExitWorktree(action: keep)` で戻る（worktree は残す。修正差分がそこにある）。切り替え後は worktree 外への書き込みや `&&`／変数代入を含む複合 Bash が拒否されることがあるので、git 操作は 1 コマンドずつ分け、scratchpad へのファイル作成は Write ツールで行う。
7. スコープ確定: `BASE=$(git merge-base origin/<baseRefName> HEAD)`、`git diff --name-only $BASE..HEAD` ＋ `git status --short` を「対象ファイル集合」として保持する。stacked PR（base が保護ブランチ以外）なら base PR の変更ファイル（`gh pr diff <basePR> --name-only`）を「衝突注意ファイル」に控える。

### 2-2. 非 PR モード

現在の checkout をそのまま使う。現在ブランチの open PR が取れれば（`gh pr view --json body`）本文を読み、2-3 の意図的決定リストに使う。

### 2-3. 意図的決定リスト（ラウンド前に 1 回）

B 判定の証拠源。次から抽出して箇条書きにし、最終レポートに「参照した意図的決定」として載せる。
- PR 本文の「設計・決定」節、および本文中の「〜は変えない」「〜は今回対象外」「〜のため〜していない」「別 PR（#N）で」
- 本文がリンクする設計ドキュメント（リポジトリ内 `docs/**` 等）の決定事項
- `git log --format=%B $BASE..HEAD` の「意図的に」「あえて」

### 2-4. 対象スキル呼び出しの組み立て

- 呼び出しは常に `Skill(skill: <target-skill>, args: <passthrough>)`。手動代替禁止。
- **スコープ注入**: PR モードで対象スキルの引数が空かつ既定が「未コミット差分」なら、対象ファイル集合をパス列で `args` に渡し、冒頭に「対象範囲: `<base>...HEAD` のコミット済み差分。`git diff HEAD` ではなく `git diff <base>...HEAD` を見る」を添える（対象スキルがネストで呼ぶ fork スキルにも範囲が伝わるように）。修正でファイルが増えたら次ラウンドで再計算する。
- 2 ラウンド目以降は `args` に「前ラウンドの修正コミット（sha と要約）」と「保留済み B の要約＋『同じ結論なら再指摘不要（"前回指摘のとおり" 1 行でよい）』」を添える。対象スキルやその fork が毎回同じ B を再報告して台帳が膨らむのを防ぐ。
- 環境の読み替え（5 章）で補助スクリプトを作った場合は、そのパスと使い方も `args` に添える（fork で動く対象スキルは親の読み替えを知らない）。
- 呼び出し直前に 1 行宣言: `--- ラウンド r/N --- 対象: <skill> / 範囲: <PR#N の差分 | 未コミット差分 | 指定ファイル> / 作業Dir: <path>`
- 対象スキルの出力に現れるパスが作業 Dir と一致するかを毎回確認する。一致しなければその出力は信用せず「環境メモ」に記録し、該当 Step は未実施扱いにする。

## 3. ループ本体

```
for r in 1..MAX:
  3-1 実行   Skill で対象スキルを丸ごと実行
  3-2 収集   出力から指摘を抽出し台帳に正規化（新規 / 再発 / 解消を判定）
  3-3 分類   各指摘を A / B / C に振る（4 章）。--dry-run ならここでレポートへ
  3-4 修正   A のみ修正（差分内に閉じる最小変更）。B / C は触らない
  3-5 検証   フォーマッタ → 修正に関係するテスト。赤 → その修正を戻して B に降格
  3-6 判定   修正しなかったラウンドで A=0 なら収束 → 7 章。そうでなければ次ラウンド
```

- **3-1**: 出力にそのスキルのレポート雛形が無い、Step が飛んでいる兆候がある（「前回と同じなので省略」等）なら実行不完全とみなし 1 回だけ再実行する。それでも欠けるなら欠けた Step を「未実施」として台帳に記録。対象スキル自身が行う修正（フォーマッタ実行など）も A として台帳に載せる。挙動が変わる修正を対象スキルがやろうとしたら止めて B に入れる。**対象スキルが fork（バックグラウンド）でテストを走らせている間は、同じ DB／リソースを使う検証を並行させない**（RefreshDatabase 等が衝突して偽の赤になる）。fork の完了通知を待ってから自分の検証を流す。
- **3-2 台帳**: `ID | key | 初出R | 最新R | 元の重要度 | 分類 | 状態 | 指摘要約 | 対応`。状態は `open / fixed / recurred / deferred(B) / excluded(C)`。指摘とみなすもの: ❌ 行、🔴🟡🟢 付き行、「問題」「修正案」「追加すべき」「未実施」「失敗テスト名」、lint / 型 / フォーマッタのエラー（「✅」「該当なし」は指摘ではない）。**重複排除キー** = 正規化パス # （シンボル名 | 10 行帯）# 指摘の種別ラベル。表現が違っても同じ場所・同じ趣旨なら同一。前ラウンドの `fixed` と同 key が再登場したら `recurred`。台帳は文脈内の表で保持し、プロジェクト内にファイルを作らない。
- **3-4 修正**: 触ってよいのは「指摘されたファイル ＋ その修正に必然的に伴うファイル（対応テスト・生成物）」のみ。ついで修正・リネームの波及禁止。1 指摘に A と B が混在（例: 「命名を直し、あわせて Service 統合を検討」）→ 分割して A 部分だけ直す。生成物は手書きせず、対象スキル／プロジェクトが示す生成コマンドで作る。テストを追加・移動するときは配置（対象メソッドのグループ内・関連テストの連続性）と隣接コメントの参照先（「上のテストのとおり」等）を同じラウンドで見直す（次ラウンドで自分の修正が 🟢 として返ってくるのを減らす）。
- **3-5 検証**: フォーマッタ → 修正ファイルに対応するテスト（対象スキル／プロジェクト規約が示す粒度。無ければ変更ファイルを参照するテストを grep で拾う）。**修正で既存テストが赤くなった、または既存テストの期待値を書き換えないと通らない = 挙動変更のシグナル** → その修正だけ戻し、B に降格して理由「修正すると <テスト名> が赤くなる」を残す。検証コマンドが環境に合わなければ 5 章の読み替え。読み替えても実行できなければ「検証未実施」を残し、収束判定は「部分収束」止まり。`--commit` ならこの後にコミット（6 章）。
- **3-6 判定**: 「収束」は**修正を行わなかったラウンド**でしか成立しない（修正した直後は必ず再実行が要る）。最終ラウンド（r = MAX）で A が出たら修正してよいが、対象スキルでの再検証はしていない旨を明示する。ラウンド末尾に 1 行: `R{r}: 指摘 X（新規 a / 再発 b / 解消 c）→ A x / B y / C z → 修正 x 件、検証 OK|NG|未実施`

## 4. 分類基準

原則（強い順）:
1. **迷ったら B**。A の条件は「直しても戻せる」ではなく「修正方法が一意で、挙動・公開 I/F・スコープを変えない」。
2. **挙動が変わるものは自動で直さない**（分岐・認可順・ステータスコード・メッセージ・ログ・メール文面・既定値・バリデーション・ミドルウェア付与・スキーマ・公開シグネチャ）。
3. **意図的決定リストに当たるものは重要度🔴でも B**（対象スキルの重要度と A/B は独立。🔴でも B、🟢でも A がある）。
4. **差分外への修正はしない**（PR が触っていない既存コードへの指摘は B「別 PR 推奨」。PR の変更が直接壊したもの＝旧参照残りは A）。
5. **A 修正は差分内に閉じ、テストは緑のまま**（3-5 の降格ルール）。
6. **一度 A で直して再発した key は B**（修正が定着しない＝前提が食い違っている）。

| 分類 | 例 |
|---|---|
| **A: 設計判断不要（即修正）** | フォーマッタ／リンタの機械的修正、未使用 import・変数、typo、コメント／PHPDoc の言語・欠落・出典コメント削除、`use` インポート、コンストラクタ省略構文、対象スキルが「同義」と明示する API 置換、テストの規約（属性形式・命名・配置・非推奨ヘルパーの同義置換）、**期待値が実装から一意に導けるテスト追加・アサーション強化（書いて緑が条件。書いたら赤 → B）**、検出力ゼロのテスト修正（変異で確認）、lint 要求の記述補完、生成コマンドで再生成できる成果物、差分から一意に決まるドキュメント追従 |
| **B: 設計判断が必要（保留してレポート）** | 挙動変更全般、公開 I/F（シグネチャ・DTO・レスポンス形・DB・Enum 値・設定/env キー名）、意図的決定に該当、構造変更（Service 統合・分割・Trait 化・Helper 切り出し・差分外リネーム）、「検討したか」形式や修正案が複数／無い指摘、テスト削除・統合・期待値に仕様判断が要るテスト、差分外の既存テスト補強、他 PR／スタックと衝突しうるファイル（衝突注意ファイル・PR 本文が言及する PR）、A の降格 |
| **C: 対象外（記録のみ）** | 偽陽性（コードを読んで前提が事実と異なると確認できたもの。根拠 1 行）、環境要因（base ブランチでも同じ失敗になるもの）、対象スキルの条件付きチェック項目が今回の差分に非該当、既に対応済みの重複 |

## 5. 終了条件と失敗時の振る舞い

- **収束**: 修正を行わなかったラウンドで A=0（B / C は残ってよい）。
- **再発停止**: 同一 key が修正後の次ラウンドで再登場 → B に昇格し、以後そのキーは触らない。全 A が再発なら「未収束（振動）」で停止。
- **無進捗停止**: 修正したのに open A の集合が前ラウンドと同一 → 停止して報告。
- **`--max` 到達**: 停止。残 A は「未対応 A」としてレポート。
- **環境要因で対象スキルの Step が失敗**: プロジェクトの CLAUDE.md・rules・memory・補助スクリプトを探し、**同じ検証内容を別の実行方法で 1 回だけ読み替える**（例: 通常 checkout 前提のコマンドを worktree／コンテナ向けの等価コマンドへ）。読み替えが複数回使われるなら scratchpad に補助スクリプト（例: `wt-php.sh`）としてまとめ、対象スキルの `args` にもパスを渡す。読み替え表（元 → 実行）はレポートの環境メモへ。読み替えても失敗 → その Step を「未実施」にして残りを続行し、収束は「部分収束（未実施: …）」までしか宣言しない。同じ環境要因で 2 ラウンド連続失敗 → 停止。読み替えは「実行方法」だけで、検証内容を弱める代替（テストを grep で代用等）は禁止。ループ開始前に読み替え後のコマンドで対象スキルの検証（テスト等）を 1 度流し、環境が緑であることを確認してから R1 に入る（環境要因の赤と修正の赤を混同しない）。
- 対象スキルが存在しない／引数解釈不能 → 使い方を出して終了。AskUserQuestion は対象解決の 1 回まで（B は溜めて最後にまとめる）。

## 6. コミット方針

- 既定は**コミットしない**。修正は作業ツリーに残し、`git status --short` と `git diff --stat` をレポートに載せる（`/fix-loop` の起動は修正の許可であって、コミットの明示依頼ではない）。
- `--commit` 指定時はラウンド（修正種別）ごとに `fix|refactor|test|docs(scope): …` でコミットする（プロジェクトのコミット規約に従う。本文に修正した指摘 ID を列挙）。開始時に未コミット差分があった場合はユーザー変更と混ざるので**コミットせず理由を書く**。
- `git add <path>` を A 修正で触ったファイルに限定（`git add .` / `-a` / amend 禁止）。B は絶対にコミットしない。
- `--push` 指定時は収束と 7 章の仕上げが済んでから `git push origin HEAD:<head>` し、CI 結果を待ってレポートに載せる（仕上げで A が出て再コミットしたときに push が二度にならないよう、push は最後に 1 回）。
- 開始時 HEAD と終了時 HEAD、修正ファイル一覧は必ずレポートに書き、ユーザーが revert しやすくする。

## 7. 仕上げ

修正差分が実装コードを含む場合、グローバル CLAUDE.md のレビュールールに従い `code-reviewer` エージェントを **1 回だけ**起動する（対象 = 開始 HEAD からの差分。worktree で作業しているときは worktree のパスとコミット範囲を明示し、メイン checkout を見ないよう伝える）。🔴 のみ A / B に分類し、A は直して 3-5 の検証、B はレポートへ。再レビューは最大 1 回。このスキル内で `code-reviewer` を多重にループさせない。

## 8. 最終レポート

チャットの最終メッセージに全文を含める（fork で動かした場合に備える）。

```
## fix-loop 完了: <target-skill> on <PR#N (branch) | 未コミット差分 | files>
状態: 収束 | 部分収束（未実施: …）| 未収束（max 到達 | 振動 | 無進捗）
ラウンド: r/N ／ 修正(A): x 件 ／ 設計判断(B): y 件 ／ 対象外(C): z 件 ／ テスト: OK|NG|未実施
作業場所: <path>（HEAD <before> → <after>）／ コミット: なし|<sha…> ／ push: なし|済（CI: …）
```

**修正した項目（A）** — 表: `ID | R | 指摘（元の重要度） | 修正内容 | ファイル | コミット`

**設計判断が必要な項目（B）** — 1 件ずつ、Yes/No で返せる粒度:
```
### B1. <指摘の要約>（元の重要度🔴、path:line）
- 指摘: <対象スキルの言葉>
- なぜ設計判断か: <挙動が変わる / 意図的決定「…」と衝突 / 差分外 / 複数案 / 再発>
- 選択肢: (1) 直す — <具体的な変更> (2) 現状維持 — <理由> (3) 別 PR
- 推奨: (n) — <一言>
- 影響: <変わる挙動・テスト・他 PR>
```
末尾に「返答例: `B1: 1, B2: 2`」。対象スキルの 🟢／任意提案（テストの統合・DataProvider の書き方・目視用テストの整え等）が複数あるときは、1 件ずつ立てずに「任意の整理提案」として 1 つの B 項目に箇条書きでまとめ、判断が要る本筋の B（挙動・I/F・意図的決定に関わるもの）と分けて見せる。

**対象外とした指摘（C）** — 表: `ID | 指摘 | 理由（偽陽性: 根拠 / 環境要因 / 非該当 / 重複）`

**参照した意図的決定** — 箇条書き（PR 本文・docs・コミットからの抜粋）

**環境メモ** — 読み替え表（元コマンド → 実行コマンド）、未実施 Step、fork の cwd ずれなど

**未収束時の状態**（該当時のみ） — 未対応 A の一覧、最終ラウンドの修正が再検証済みか、次に回すべきコマンド 1 行

**修正差分** — `git status --short` ＋ `git diff --stat`（`--commit` 時はコミット一覧）

## 9. やってはいけないこと
